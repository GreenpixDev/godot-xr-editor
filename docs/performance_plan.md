# План работ: 72 fps на больших графах и сценах

Составлен 2026-11-09 по замерам из [quest_graph_performance.md](quest_graph_performance.md) (D-151…D-156). Состояние на эту дату: открытый BlueCube в редакторе на Quest 2 — 57–60 fps (App 14,1–14,9 мс при бюджете ~12,6); граф ×2 и ×4 — ниже; на ПК предел — CPU (время кадра 8,1–8,6 мс на ×1, 13 на ×2, 24 на ×4).

## Цель

- **Quest 2, редактор:** ≥72 fps при открытом графе; GPU приложения ≤12,6 мс, кадр ≤13,9 мс.
- **ПК (RTX 4060), редактор:** ≥72 fps; кадр ≤13,9 мс.
- **Масштаб:** цена графа и редактора зависит от того, что видно и что меняется, а не от размера всего графа и сцены.
- **Сцена пользователя:** 72 fps для любой сцены не гарантируется. Если сцена тяжелее бюджета как игра, помогают только режимы с потерями, их выбирает пользователь.

Критерии готовности (уточнить с автором):

- BlueCube ×1 и ×2 — 72 fps на Quest без потерь при настройках по умолчанию.
- ×4 — 72 fps с деталями по расстоянию.
- ПК: ×4 — кадр ≤13,9 мс.

## Правила для всех шагов

- **Настройка на каждый приём:** значение `XREFeatureSettings` в новом разделе «Графика» (инвариант 7). Старый путь остаётся вариантом для сравнения. Какой вариант первый, то есть по умолчанию, решаем с автором по каждой настройке. Тест на каждый вариант и запись в `decisions.md` о сравнении.
- **Замер до и после каждого приёма** тем же прогоном лаборатории. Числа только из замеров; оценки ниже — ориентир, не результат.
- **Вид:** снимок `shot_blueprint_vr.gd` и сверка с макетом до отчёта. Поведение в шлеме подтверждает автор.
- **Форк движка — крайний случай** ([D-157](decisions.md)): только когда обхода в GDScript или GDExtension нет и замер показывает, что упираемся в движок. Затем PR в upstream.

Ограничения:

- **ovrgpuprofiler:** подробный режим включается на приложение целиком и добавляет ~10 % к GPU. Числа VrApi такого прогона сравнивать только внутри прогона. Эталон без профайлера — прогон D-155.
- **Compatibility на Android:** встроенные GPU-метки движка (1.1, 1.3) не пишутся. Это видно в `drivers/gles3/storage/utilities.cpp` 4.7.2: `glQueryCounter` только на desktop GL. Там остаются VrApi и ovrgpuprofiler.
- **`--gpu-profile`:** складывает стадии с одним именем по всем вьюпортам. На Mobile основной проход, прозрачность и тонмаппинг идут одной меткой.

Первый прогон этапа — уже подготовленный `--xre-graph-lab-base` (раздел «Прогон: база GPU в редакторе» в [quest_graph_performance.md](quest_graph_performance.md)) с добавленными 1.1 и 1.2.

## Этап 4. CPU в несколько потоков

Что известно по исходникам 4.7.2:

- **Редактор не может рисовать в отдельном потоке.** В `main/main.cpp` при запуске редактора `separate_thread_render = 0` (комментарий: иначе падает при старте). Скрипты и подготовка отрисовки идут в одном главном потоке.
- **Отсечение уже параллельное.** `RendererSceneCull` раскладывает его по `WorkerThreadPool`, когда объектов больше порога.
- **Игровой процесс** может включить `rendering/driver/threads/thread_model = Separate`; движок помечает режим как экспериментальный.

| # | Приём | Суть | Ограничения |
|---|---|---|---|
| 4.1 | Работу — на GPU | Шаги 2.2 и 2.3: на ПК у GPU большой запас | — |
| 4.2 | `WorkerThreadPool` для чистых вычислений | Раскладка, кривые проводов, построение буферов `MultiMesh` и мешей текста, выбор уровня детализации. Результат применяется на главном потоке | Дерево сцены из рабочих потоков не трогать |
