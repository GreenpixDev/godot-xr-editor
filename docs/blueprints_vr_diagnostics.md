Нет покадрового CPU/GPU CSV и временных меток действий пользователя. Поэтому ухудшение темпа установлено, его полная причина и соблюдение бюджета 11,1 мс не установлены.

## Два потока ошибок

| Ошибка в engine-логе | Число | Происхождение и исправление |
|---|---:|---|
| `XREPicker: set the scenario first.` | 19 348 | Вызов `cast_segment` из `XREBlueprints._update_pointer`, пока активен Pick Target; scenario не задан. Установленная причина невозможности выбрать куб. Теперь назначается общий World3D.scenario. |
| `Condition "active_sets.is_empty()" is true. Returning: false` | 180 030 | Штатный `OpenXRAPI::sync_action_sets`, `modules/openxr/openxr_api.cpp:3803`. Пустой action map редактора (D-005), отдельный action set контроллеров синхронизирует наша GDExtension. Этот поток остаётся. |

В начале лога уже есть успешное `controller action set attached to the editor's OpenXR session`, затем ошибка штатного attach и `active_sets.is_empty()` — ещё до работы с Blueprint. В `gdextension/src/editor_controllers.cpp` `_on_session_created` присоединяет собственный набор, а `_on_process` вызывает `xrSyncActions` с одним активным набором. Собственная ошибка синхронизации выводится однократно до восстановления, а не каждый кадр. Таким образом, `active_sets.is_empty()` относится к пустому списку движка, а не к набору нашего контроллера.

Без группировки дубликатов Output этот поток уже вызывал дорогие удаления строк и просадку в прежнем спайке (D-004/D-005). В данном запуске нет предупреждения о выключенной группировке, но нет трассы её состояния в каждом интервале. Считать этот механизм доказанной причиной именно текущей просадки нельзя. Исправление пикера убирает дополнительный поток сообщений и стектрейсов; выигрыш в FPS ещё не измерен.

## Повторный замер

Проверка кода не выявила обхода проекта или создания карточек/проводов в каждом кадре: каталог и значки перестраиваются по событиям, карточки — после изменений документа; попадания проверяются по кешированным карточкам/портам. В старом коде preview дважды обновлялся разными руками за кадр — теперь только владельцем. Кеш геометрии виджета заполняется по выбору/структурным событиям, а в кадре читаются трансформы и AABB. Число карточек/портов и частей выбранной группы всё ещё влияет на стоимость обработки; её не измеряли. Первое создание материалов и первый расчёт рёбер меша могут давать отдельные длинные кадры (D-020), но этим нельзя объяснить весь длительный участок 31–44 FPS без профиля.

В основном проекте `C:/Users/aniku/Projects/godot-xr-editor` с перенесёнными исправлениями запустить:

```powershell
py scripts/xr_editor.py res://benchmarks/play_check.tscn -- --xre-session-frames
```

Убедиться, что группировка дубликатов Output включена. После прогрева выполнить по отдельности: сцена с закрытым графом; открытый граф без движения; наведение/перенос карточки и предварительный провод; Pick Target по кубу; закрытый граф; один Y → игра → удержание Y → редактор; снова открытый граф. Держать каждый стационарный этап примерно 30 с и записать время начала действия по часам. Не сворачивать редактор.

Прислать новый engine-лог, `benchmarks/results/frametime_*.csv` и соответствующий `_meta.json` (точные пути печатает запись), список времён этапов и рантайм. По CSV сравнить CPU/GPU и долю кадров в бюджете по этим этапам, переходы вынести отдельно. Этот замер не запускался без пользователя и не заменён headless-тестом. Постоянный виджет FPS остаётся отдельным backlog.
