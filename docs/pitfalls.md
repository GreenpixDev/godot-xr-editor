# Подводные камни OpenXR, Quest, SteamVR и Windows

Вынесено из CLAUDE.md. Читать при работе с XR-сессией, нативной частью, автономным шлемом, play-mode и панелями в шлеме. Общие подводные камни Godot 4.7 остались в CLAUDE.md.

- **OpenXR в редакторе** (по исходникам 4.7.2, `modules/openxr`, и логам запусков на Quest 2 по Link 2026-10-05; контроль — обычная XR-игра на том же 4.7.2 — работает):
  - Godot рассчитывает на один `xrWaitFrame` (`XRServer::_process`) на одну отрисовку (`xrBeginFrame`/`xrEndFrame` внутри `RenderingServer::draw()`) в каждой итерации главного цикла. Редактор это нарушает дважды: low-processor mode пропускает отрисовку, а окна прогресса (`ProgressDialog::_update_ui`, при старте — «Project initialization») и ещё несколько мест вызывают `Main::iteration()` изнутри итерации. Вложенный `xrWaitFrame` приходит до начала внешнего кадра; рантайм Meta ждёт ~30 с, отвечает `XR_ERROR_RUNTIME_FAILURE` и теряет сессию. Нативный `XREEditorFrameLoop` выключает low-processor mode после каждого ожидания и перед каждым ожиданием дорисовывает неначатый кадр через `RenderingServer.force_draw()`; после этого движок печатает безвредные `CALL_ORDER_INVALID` внешней отрисовки. GDScript возвращает low-processor mode только после конца сессии;
  - редактор всегда рендерит в одном потоке (`Main::setup` принудительно), поэтому `force_draw()` рисует синхронно;
  - action map проекта не грузится: в редакторе вызывается `OpenXRActionMap::create_editor_action_sets()`, а она пустая (`// TODO implement`). Контроллеры даёт наш `XREEditorControllers` (gdextension/): свой action set, привязанный к сессии раньше движка. Движок всё равно печатает `OpenXR: failed to attach action sets!` и каждый кадр — ошибку `active_sets.is_empty()` из `OpenXRAPI::sync_action_sets`: это шум движка, не наш баг;
  - эта ежекадровая ошибка не безобидна: без группировки дубликатов (кнопка Collapse в панели Output, настройка `_editor_log_collapse`) каждая добавляет строку в Output, а после `run/output/max_lines` (10 000, ≈ 111 с при 90 Гц) каждое сообщение удаляет первую строку RichTextLabel — CPU главного потока растёт с ~1–3 до 10–16 мс, и рантайм уходит на 45 Гц (замеры 2026-10-05, `benchmarks/results/`). `Engine.print_error_messages = false` не помогает: обработчики ошибок редактора вызываются всегда. `Engine.set_editor_hint` в GDExtension недоступен, так что убрать ошибку у источника можно только правкой движка (кандидат на PR);
  - обёртку OpenXR (`OpenXRExtensionWrapper`) можно зарегистрировать только до создания инстанса (уровень SERVERS), поэтому библиотека регистрирует обе обёртки на уровне CORE, в любом запуске редактора: без `--xr-mode on` сессии нет и их никто не вызывает. Удаляет обёртки сам движок при выходе — освобождать их нельзя;
  - сессия создаётся (`_on_session_created`) при инициализации модулей SCENE, до `register_server_singletons()`: в этот момент `XRServer::get_singleton()` из GDExtension возвращает null (было падение). К синглтонам серверов обращаться с первого кадра (`_on_process`), при выходе — только после `Engine.has_singleton()`;
  - `OS.get_cmdline_args()` не содержит аргументов, которые разобрал сам движок (`--path`, `--headless`, `--xr-mode` …): по нему режим XR не узнать;
  - редактор грузит GDExtension при старте, только если она уже есть в `.godot/extension_list.cfg`; найденная на ходу загрузится слишком поздно для OpenXR. `build_gdextension.sh` обновляет список headless-импортом;
  - настройки проекта `xr/openxr/*` (reference space, form factor, blend mode) игнорируются, пространство по умолчанию — STAGE;
  - `XROrigin3D` не передаёт свой transform в `XRServer.world_origin` — это делает `XRERig`;
  - модели контроллеров от рантайма (`OpenXRRenderModelManager`) в редакторе не появятся, даже если рантайм их даёт: расширение движка обновляется в `on_sync_actions`, а его вызывает только успешный `sync_action_sets`. Рантайм Meta по Link таких расширений и не даёт, поэтому модели статические (D-010);
  - сессия создаётся при старте, на уровне инициализации SCENE: до загрузки плагинов и до GDExtension уровня SCENE;
  - `OpenXRCompositionLayer*` в редакторе всегда рисуется запасным мешем (`_should_use_fallback_node` проверяет `is_editor_hint`): слоем композиции, который компоновщик держит сам, пока приложение занято, он там не становится (D-019).
- **Автономный шлем, Horizon OS** (по исходникам 4.7.2, `platform/android/java/editor`, и прогонам на Quest 2 2026-10-06/07, D-017, D-018):
  - редактор — Android-приложение `org.godotengine.editor.v4.meta`. У него два вида окон: 2D-панель и окно с погружением для XR-игр (процесс `:GodotXRGame`). Запуск с `--editor` всегда уходит в панель, а окно игры, увидев `--editor`, перезапускает себя панелью. VR открывается путём к `project.godot` в аргументах (`XREStandalone.open_editor_in_vr`);
  - запуск из окна с погружением чего-то, что тоже идёт в это окно (игры из редактора, редактора из игры), перезапускает процесс (`triggerRebirth`). Редактор и XR-игра одновременно не живут, отладчика у такой игры нет;
  - после запуска игры редактор ещё 2–3 с закрывает движок с открытой сессией OpenXR, и шлем показывает его последний кадр, повёрнутый за головой. Поэтому вид закрывается до запуска (`XRETransitionScreen`, D-019). Чёрный экран между процессами рисует система, а её заставку задаёт манифест APK редактора;
  - холодный старт редактора в VR — около 11 с до главного цикла (9,6–14,3 с), плагин грузится ещё через ~2 с. Этот чёрный экран плагин не закроет. `--benchmark` (`quest.py --engine=--benchmark`) в logcat ничего не вывел (D-019);
  - `OS.has_feature("xr_editor")` истинно в редакторе на шлеме и в играх, которые он запускает; в экспортированной игре и на ПК — ложно;
  - GDExtension из проекта на `/sdcard` Android копирует во внутреннюю память и грузит оттуда. При старте грузится, только если она уже есть в `.godot/extension_list.cfg`, а его пишет скан редактора на панели. Поэтому `XREStandaloneLauncher` открывает VR после скана;
  - без нативной части темп кадров ломается на первом же кадре: рантайм держит `xrWaitFrame` 1 с и отвечает `XR_ERROR_RUNTIME_FAILURE`, кадры идут раз в секунду. Сбрасывает это только снятие и надевание шлема;
  - вывод редактора виден только в logcat (тег `godot`), панель Output в шлеме не видна. Чтобы спрятать невидимый интерфейс редактора, прятать `EditorInterface.get_base_control()`: выключенный корневой вьюпорт гасит и XR-вид, который лежит в его дереве;
  - GPU — главный предел. Невидимый интерфейс редактора с 3D-вьюпортом стоил ~13 мс на кадр (теперь спрятан), один источник света — 3,5–4 мс (поэтому фовеальный рендеринг, D-018). Темп кадров приложения лучше брать из счётчиков рантайма Meta (logcat `VrApi`, раз в секунду: `FPS`, `Stale`, `App` — GPU мс, `GPU%`): `benchmarks/quest_fps_report.py`;
  - `adb push --sync` копирует любой файл с другим временем, а не только более новый: без проверки `quest.py` затирал сцены, сохранённые в шлеме;
  - Не предполагать, что инструменты доступны в каталоге проекта или в конкретном `AppData`: проверять фактические пути Godot, NDK и SDK перед запуском сборки.
- SteamVR 2.17.10 настраивает как приложение в фокусе (захват фокуса сцены и «продвинутая обработка текстур сцены» в `Steam/logs/xrclient_<exe>.txt`) только первую OpenXR-сессию процесса. Сессия, созданная в том же процессе заново (`XRESession.reacquire_session`), их не получает при любом порядке действий и отдаёт кадры композитору медленнее: кадр, в котором перерисовывается окно редактора, опаздывает (D-012).
- SteamVR оставляет себе левую кнопку Menu на Touch: она открывает дашборд SteamVR, приложение нажатия не получает. Для своих действий брать A/B/X/Y и стики.
- Windows блокирует загруженную DLL: пока редактор открыт, библиотеку не пересобрать (`reloadable = false` — горячая перезагрузка оставила бы движку висячий указатель на обёртку).
- Второй редактор на том же проекте не загрузит нативную библиотеку (её копию `~xre_native…dll` держит первый) и стартует без обходов D-005: VR в нём не работает, плагин не грузится. `scripts/xr_editor.py` поэтому закрывает открытый редактор проекта перед запуском.
- В `build/`, `gdextension/` и `benchmarks/results/` лежит `.gdignore`: иначе Godot сканирует тысячи C++-файлов как ресурсы, а каждый `.csv` импортирует как файл переводов (по `.translation` на столбец).
- Запись файла посреди замера кадра (CSV между сегментами) давала заминку главного цикла, после которой рантайм Meta уходил на 45 Гц и при видимом UI не возвращался (наблюдение 2026-10-05). `XREFrameTimer` копит весь прогон в памяти и пишет один CSV в конце.
- `XRCamera3D` и `XRController3D` следуют за трекерами и в редакторе (`scene/3d/xr/xr_nodes.cpp` без проверки `is_editor_hint`). Игрок XR-игры, сохранённый в редактируемой сцене, в шлеме двигается за головой и руками: трансформы попадут в .tscn, а меши его контроллеров перехватывают луч. `benchmarks/play_check.tscn` поэтому создаёт игрока при запуске игры (D-011).
- Сцена без XR-игрока в play-mode даёт в шлеме чёрный экран: игра забирает шлем, но рисовать ей нечего. В логе игры — `OpenXR: No viewport was marked with use_xr`. Лог игры не попадает в лог редактора: он лежит в `%APPDATA%\Godot\app_userdata\XR Editor (dev)\logs\godot.log`. Play-mode проверять на `play_check.tscn`.
- Игра, запущенная из редактора, не получает его `--xr-mode` (флаг пересылается только инструментам, `Main::get_forwardable_cli_arguments`); `EditorPlugin._run_scene` видит только аргументы из меню запуска, а не всю командную строку игры. Неизвестный движку аргумент до `--` (как `--xre-play`) доходит до `OS.get_cmdline_args()`.
- Мышь в `SubViewport` через `push_input` (панели в шлеме, D-016): события в логических координатах (`in_local_coords = true` при `size_2d_override`); наведение работает только после `notification(NOTIFICATION_VP_MOUSE_ENTER)`, уход — `NOTIFICATION_VP_MOUSE_EXIT`; флаг `double_click` движок не ставит (это делает платформа) — его размечает `XREPanelSurface`.
- `EditorInspector` пишет в объект мимо `XREDocument` и сам создаёт запись undo. Объект с методом `_dont_undo_redo() -> true` он только `set()`-ит; `_hide_script_from_inspector` и `_hide_metadata_from_inspector` прячут скрипт и кнопку метаданных (`XREInspectorProxy`). При переключении вкладки сцены редактор восстанавливает её выбор.
- Удалённая через `remove_child` нода теряет `owner` у себя и потомков, если владелец больше не предок. Undo удаления должен восстанавливать owner — см. `XREPluginDocument.remove_node`.
- Импорт glTF по умолчанию вынимает встроенные текстуры в файлы рядом с `.glb` с флагом `detect_3d`: при первом показе в 3D редактор сам переимпортирует их со сжатием и перепишет `.import`. У моделей контроллеров сжатие задано явно (`compress/mode=2`, `detect_3d/compress_to=0`). Встроенные в сцену текстуры (`gltf/embedded_image_handling=3`) обходятся без лишних файлов, но остаются без mipmaps.
