# CLAUDE.md

VR-редактор сцен для Godot 4.7 в виде EditorPlugin — дипломная работа (октябрь 2026 — июнь 2027). Задача — собрать сцену, оживить её логикой и протестировать, не снимая шлем, и честно измерить, где VR выигрывает у настольного редактора, а где проигрывает. Рабочая база — прототип, но научный результат — это паттерны взаимодействия и числа из эксперимента.

- [docs/plan.md](docs/plan.md) — источник истины: RQ1–RQ3, MVP, архитектура, задачи эксперимента T1–T3, риски, сроки.
- [docs/decisions.md](docs/decisions.md) — дневник решений (D-001…).

## Текущий этап

Спайк «XR в процессе редактора» закрыт 2026-10-05 решением **D-004: остаёмся в EditorPlugin**. На Quest 2 по Link при 90 Гц на пустой сцене 100 % кадров ≤ 11,1 мс и с открытым 2D-UI (p99 4,2 мс), и со скрытым (p99 2,0 мс); передача шлема игре — медиана 2,3 с, обратно — 0,05 с. Условия: обходы движка в `gdextension/` (D-005) и включённая группировка дубликатов в панели Output (см. «Подводные камни»).

Дальше — по плану (раздел «Следующие шаги» и дорожная карта): UI и инструменты VR-слоя теперь можно писать. Открыто из спайка: замер передачи шлема на SteamVR (план требует оба рантайма), PR в upstream по двум дефектам движка (D-004), сборка движка с отладочными символами — не понадобилась.

*Обновлять этот раздел при переходе к следующему этапу.*

## Жёсткие ограничения

- **Godot 4.7.x, без обновлений** до конца исследования (условие воспроизводимости). Установлен 4.7.2: `godot` в Git Bash, `godot.cmd` в PowerShell → `%LOCALAPPDATA%\Programs\Godot\`. API из 4.8+ не использовать.
- **Объём.** Функция входит, только если нужна для задач T1–T3 (таблица MVP в плане). Всё остальное — в future work, не в код. Если просят что-то вне MVP — сказать об этом, прежде чем делать.
- **Движок не форкаем.** Не хватает хука — обход в GDScript/GDExtension, затем PR в upstream. Локальных патчей движка нет.
- **Нативная часть закреплена так же:** godot-cpp 10.0.0-stable (сабмодуль) с API 4.7, заголовки OpenXR 1.1.54 (те же, что в Godot 4.7.2), MSVC 14.51 из Visual Studio 2026. Смена любой версии — запись в дневнике решений.
- **Данные участников** (аудио, анкеты, логи с идентификаторами) никогда не попадают в git: только `study/data/raw/` (в .gitignore).

## Архитектурные инварианты

Отступление от любого пункта — только с записью в `docs/decisions.md`.

1. **Сцена меняется только через `XREDocument`** ([core/document.gd](addons/xr_editor/core/document.gd)). Инструменты, UI и граф не вызывают `EditorInterface` / `EditorUndoRedoManager` и не пишут в редактируемые ноды напрямую. Перетаскивание — `preview_transform` каждый кадр и один `commit_transform` в конце. Так действие из шлема отменяется с клавиатуры, попадает в лог и не ломает запасной путь.
2. **VR-слой не попадает в .tscn.** Риг, руки, меню, гизмо живут в дереве редактора (под плагином / его SubViewport), никогда под `get_edited_scene_root()` и без `owner`. Они рисуются на отдельном visual layer, скрытом от камеры настольного 3D-вьюпорта.
3. **Один `World3D`, никаких копий.** XR-`SubViewport` (`use_xr = true`) берёт `world_3d` 3D-вьюпорта редактора. Код синхронизации плоского и VR-вида не пишется — синхронизировать нечего.
4. **Бюджет кадра 11,1 мс.** В покадровом коде нет аллокаций, поиска по дереву (`get_node`, `find_child`) и рейкастов по всей сцене; горячие пути — в GDExtension. При входе в VR low-processor mode выключается, ограничение FPS снимается.
5. **Каждая операция пользователя логируема**: тип, источник (3D-инструмент или 2D-панель), время. Доля операций через панели — метрика исследования; операция в обход документа — потерянные данные.
6. **Граф логики** хранится ресурсом `.tres` рядом со сценой и компилируется в читаемый `.gd` на ноде. Исходник — граф, артефакт — GDScript.

## Структура

```
addons/xr_editor/          плагин (всё, что поставляется)
  plugin.cfg, plugin.gd    точка входа EditorPlugin; владеет XREDocument
  core/                    XREDocument и его реализации
  xr/                      XR-сессия в процессе редактора (XRESession) и риг (XRERig)
  telemetry/               замеры спайка: время кадра (XREFrameBenchmark), передача шлема игре (XREHandoffBenchmark)
  xr_editor.gdextension    подключение нативной библиотеки
  bin/                     собранная библиотека (не в git, собирает scripts/build_gdextension.sh)
gdextension/               C++ (GDExtension): src/, godot-cpp/ (сабмодуль), thirdparty/openxr/
benchmarks/                эталонные сцены (empty, xr_view_check, xr_game_check — контрольная XR-игра, xr_handoff_game — игра для замера передачи),
                           frametime_report.py (отчёт по замеру), results/ (сырые CSV и отчёты замеров, в git)
project.godot              хост-проект для разработки (OpenXR и XR-шейдеры включены)
openxr_action_map.tres     action map по умолчанию, создан Godot (в редакторе не используется)
scripts/check.sh           проверка без шлема
scripts/parse_all.gd       загрузчик всех скриптов для check.sh
scripts/build_gdextension.sh  сборка нативной части (MSVC + CMake + Ninja из Visual Studio)
docs/                      план и дневник решений (на русском)
```

Модули по мере надобности — не заводить пустыми папками: в аддоне `tools/` (выбор, манипуляция, снап), `ui/` (палитра, радиальное меню, панели-текстуры), `logic_graph/`, `playmode/` (передача OpenXR-сессии), `telemetry/`; в корне `study/` (протокол, анкеты, анализ).

## Команды

```bash
scripts/check.sh                              # все скрипты парсятся и типизированы, нативная библиотека и плагин грузятся в headless-редакторе
scripts/build_gdextension.sh                  # собрать gdextension/ в addons/xr_editor/bin/ (редактор перед этим закрыть)
godot --path . --editor                       # обычный редактор
godot --path . --editor --xr-mode on          # редактор с принудительным OpenXR (спайк)
mkdir -p logs && godot --path . --editor --xr-mode on --log-file logs/xr.log   # то же с логом в файл
godot --path . --log-file logs/xr_game.log res://benchmarks/xr_game_check.tscn  # контроль: обычная XR-игра без редактора
py benchmarks/frametime_report.py benchmarks/results/frametime_<stamp>.csv  # сводка, гистограмма и график замера кадра
godot --path . --editor --xr-mode on --log-file logs/xr_handoff.log -- --xre-handoff  # замер передачи шлема игре и обратно
```

Замер кадра (Link на 90 Гц): `godot --path . --editor --xr-mode on --log-file logs/xr_bench.log res://benchmarks/empty.tscn -- --xre-benchmark` → надеть шлем; замер ждёт состояния FOCUSED, идёт ~4 мин (сегменты ABBA: UI открыт / скрыт / скрыт / открыт) и сам закрывает редактор. Меню и диалоги редактора во время замера не трогать: это отдельные окна, они сбивают темп кадров. Тот же замер есть в Project → Tools (в русском интерфейсе — Проект → Инструменты) → «XR Editor: Measure Frame Time», без автозакрытия. Результаты — в `benchmarks/results/`. Метрики и их смысл — в `gdextension/src/frame_timer.h` и в docstring `frametime_report.py`.

## Проверка

- После любого изменения GDScript — `scripts/check.sh`, должен закончиться `check: OK`. После изменения C++ — сначала `scripts/build_gdextension.sh` (сборка без предупреждений на /W4), затем `scripts/check.sh`.
- Поведение в шлеме Claude проверить не может. Для VR-изменений — дать короткий чек-лист: что запустить, что сделать руками, что должно произойти, какой вывод или замер прислать обратно. Не писать «работает», пока пользователь не подтвердил.
- Числа (время кадра, задержки, проценты) — только из замеров, не из оценок.

## Код

- GDScript 4.7, `@tool` на каждом скрипте аддона: они исполняются в редакторе.
- **Статическая типизация обязательна и проверяется движком** (D-003): `untyped_declaration` = ошибка, включая параметры, возвраты и переменные цикла (`for node: Node in nodes`). `:=` допустим. С 2026-10-05 ошибки также `unsafe_property_access` и `unsafe_method_access`: обращение к несуществующему свойству (`SubViewport.update_mode`) иначе всплывает только в шлеме.
- Глобальные классы с префиксом `XRE` (`XREDocument`); файлы в snake_case; отступы табами.
- Код, идентификаторы, комментарии и сообщения коммитов — на английском. Документация в `docs/` и общение — на русском.
- `##` doc-комментарии на публичных классах и методах: из них генерируется справка API для приложения к диплому.
- Сигналы редактора, подключённые в `_enter_tree`, отключаются в `_exit_tree`: плагин перезагружается при каждом выключении/включении.
- C++ (`gdextension/src/`): C++17, стиль кода движка (табы, `p_` у параметров, `r_` у выходных). Классы, видимые в ClassDB, тоже с префиксом `XRE`. Покадровый код не аллоцирует: `StringName` и буферы готовятся заранее.

## Подводные камни Godot 4.7

- Предупреждения GDScript в `addons/` по умолчанию выключены. Наш аддон включён через `debug/gdscript/warnings/directory_rules` в `project.godot` (`1` — включить). Не удалять.
- `load()` возвращает объект скрипта даже при ошибке парсинга; сломанный скрипт отличает только `can_instantiate() == false`.
- Headless-запуск проекта без `--xr-mode off` пытается поднять OpenXR (он включён в настройках) и сыплет ошибками.
- Рядом со скриптами лежат `*.gd.uid` — коммитить. Переименовывать и перемещать скрипты вместе с `.uid` (или из редактора).
- `--log-file` не создаёт папку: без существующей `logs/` лог молча не пишется.
- Свёрнутое окно редактора усыпляет главный цикл (`OS::add_frame_delay` при `window_can_draw() == false`) — в VR окно не сворачивать, фокус терять можно.
- **OpenXR в редакторе** (по исходникам 4.7.2, `modules/openxr`, и логам запусков на Quest 2 по Link 2026-10-05; контроль — обычная XR-игра на том же 4.7.2 — работает):
  - Godot рассчитывает на один `xrWaitFrame` (`XRServer::_process`) на одну отрисовку (`xrBeginFrame`/`xrEndFrame` внутри `RenderingServer::draw()`) в каждой итерации главного цикла. Редактор это нарушает дважды: low-processor mode пропускает отрисовку, а окна прогресса (`ProgressDialog::_update_ui`, при старте — «Project initialization») и ещё несколько мест вызывают `Main::iteration()` изнутри итерации. Вложенный `xrWaitFrame` приходит до начала внешнего кадра; рантайм Meta ждёт ~30 с, отвечает `XR_ERROR_RUNTIME_FAILURE` и теряет сессию. Нативный `XREEditorFrameLoop` выключает low-processor mode после каждого ожидания и перед каждым ожиданием дорисовывает неначатый кадр через `RenderingServer.force_draw()`; после этого движок печатает безвредные `CALL_ORDER_INVALID` внешней отрисовки. GDScript возвращает low-processor mode только после конца сессии;
  - редактор всегда рендерит в одном потоке (`Main::setup` принудительно), поэтому `force_draw()` рисует синхронно;
  - action map проекта не грузится: в редакторе вызывается `OpenXRActionMap::create_editor_action_sets()`, а она пустая (`// TODO implement`). Контроллеры даёт наш `XREEditorControllers` (gdextension/): свой action set, привязанный к сессии раньше движка. Движок всё равно печатает `OpenXR: failed to attach action sets!` и каждый кадр — ошибку `active_sets.is_empty()` из `OpenXRAPI::sync_action_sets`: это шум движка, не наш баг;
  - эта ежекадровая ошибка не безобидна: без группировки дубликатов (кнопка Collapse в панели Output, настройка `_editor_log_collapse`) каждая добавляет строку в Output, а после `run/output/max_lines` (10 000, ≈ 111 с при 90 Гц) каждое сообщение удаляет первую строку RichTextLabel — CPU главного потока растёт с ~1–3 до 10–16 мс, и рантайм уходит на 45 Гц (замеры 2026-10-05, `benchmarks/results/`). `Engine.print_error_messages = false` не помогает: обработчики ошибок редактора вызываются всегда. `Engine.set_editor_hint` в GDExtension недоступен, так что убрать ошибку у источника можно только правкой движка (кандидат на PR);
  - обёртку OpenXR (`OpenXRExtensionWrapper`) можно зарегистрировать только до создания инстанса (уровень SERVERS), поэтому библиотека регистрирует обе обёртки на уровне CORE, в любом запуске редактора: без `--xr-mode on` сессии нет и их никто не вызывает. Удаляет обёртки сам движок при выходе — освобождать их нельзя;
  - сессия создаётся (`_on_session_created`) при инициализации модулей SCENE, до `register_server_singletons()`: в этот момент `XRServer::get_singleton()` из GDExtension возвращает null (было падение). К синглтонам серверов обращаться с первого кадра (`_on_process`), при выходе — только после `Engine.has_singleton()`;
  - `OS.get_cmdline_args()` не содержит аргументов, которые разобрал сам движок (`--path`, `--headless`, `--xr-mode` …): по нему режим XR не узнать;
  - редактор грузит GDExtension при старте, только если она уже есть в `.godot/extension_list.cfg`; найденная на ходу загрузится слишком поздно для OpenXR. `build_gdextension.sh` обновляет список headless-импортом;
  - настройки проекта `xr/openxr/*` (reference space, form factor, blend mode) игнорируются, пространство по умолчанию — STAGE;
  - `XROrigin3D` не передаёт свой transform в `XRServer.world_origin` — это делает `XRERig`;
  - сессия создаётся при старте, на уровне инициализации SCENE: до загрузки плагинов и до GDExtension уровня SCENE.
- Windows блокирует загруженную DLL: пока редактор открыт, библиотеку не пересобрать (`reloadable = false` — горячая перезагрузка оставила бы движку висячий указатель на обёртку).
- В `build/`, `gdextension/` и `benchmarks/results/` лежит `.gdignore`: иначе Godot сканирует тысячи C++-файлов как ресурсы, а каждый `.csv` импортирует как файл переводов (по `.translation` на столбец).
- Запись файла посреди замера кадра (CSV между сегментами) давала заминку главного цикла, после которой рантайм Meta уходил на 45 Гц и при видимом UI не возвращался (наблюдение 2026-10-05). `XREFrameTimer` копит весь прогон в памяти и пишет один CSV в конце.
- Удалённая через `remove_child` нода теряет `owner` у себя и потомков, если владелец больше не предок. Undo удаления должен восстанавливать owner — см. `XREPluginDocument.remove_node`.
